# Jobs

In every mapped project the session the user types into is the cockpit, and each role request runs as a job: a background subagent `tedy:<role>` that the cockpit starts with the Agent tool from the spec `node <plugin>/scripts/job.mjs start` prints. `<plugin>` is the plugin root. A job file is `plans/jobs/<yymmdd-hhmm>-<role>-<slug>.md` under the map's `paths[0]`, with this header: `to: tedy:<role>`, `from: cockpit`, `status`, `created`, `title`, `cwd`, and for a dev job with a repository `repo`, `branch`, `base`, `worktree` and `worktree_owner: core`, then the request and its sections. A job file v0.2.24 or v0.2.25 wrote may also hold `permission_mode` and `session_id` in its header; the kit reads past them. The job's agent id, the cockpit's session and claude process, and the job's state live in its launch record in the state dir, written by the kit's hooks. A job lives inside the cockpit session and ends with it.

## Which agent this is

A subagent whose `agent_type` is `tedy:<role>` and whose prompt starts with the kit's launch form `Job file "<file>"` is that job; the path sits in double quotes with JSON escapes, so a project folder whose path holds a space or a quote binds too. The hooks read that form at the head of the agent's own transcript on its first tool event and bind its `agent_id` to the job. The first such agent is the job's agent, whose id `resume` sends to; every later agent whose launch form names the same job file is recorded under `agents` in the record with its own state, and `close`, `resume` and `prune` hold while any recorded agent runs. The role gate gives the agent its job's role from that form whether the record is bound to it, to another agent or to none, and from the record that names its id, so a second agent sent to the same job keeps every job ask, after the job is closed too. For such an agent the gate takes the project map from the job file, never from the folder the agent works in, so its asks hold in a core worktree outside every map path. A job path anywhere else in the prompt binds nothing. The main thread of any session is the cockpit, unless it runs as `claude --agent tedy:<role>`, which keeps that role.

## Cockpit

1. Do no role work: read only what picking the owner needs. Tracker, PRD, Doc or Figma → `pm`; a PR review → `review`; code in a repository → `dev` with `--repo <path>`; deploy or infrastructure → `devops`. Read-only questions the cockpit may answer itself.
2. Typing a request is the user's approval to start its job. Ask one `AskUserQuestion` only when the owner is unclear or the request spans two roles, and split such a request into one job per role.
3. Spawn with Agent. Write the user's words verbatim into a temporary file, followed by `## User decisions` (what the user settled, or "none yet"), `## First safe step` (one read-only step) and `## Sources` (locators). Then run `node <plugin>/scripts/job.mjs start <pm|dev|review|devops> --title "<short title>" --body-file <file> [--repo <path>] [--branch <name>]`. It writes the job file and its launch record and prints one JSON object: `subagent_type`, `run_in_background`, `name` (`<role>-<yymmddhhmm>-<slug>` from the job file, cut to 32 characters with the stamp kept; `start` refuses and writes nothing when an open job already has that name), `description` and `prompt`. Call the Agent tool with exactly those five fields, unchanged, and reply with the job's name and file. Never do the job's work in the cockpit, never drop `run_in_background`, and never run a job from the cockpit's Bash. A dev job with `--repo` works in its own worktree, which `start` makes with `git worktree add` on `--branch` (default `feat/<title slug>`) from the map's integration branch (the repo's `branch`, else `origin/HEAD`), under `<repo parent>/.worktrees` or the map's `worktree_root`; the job file's `cwd` names it. Start at most one dev job per repository at a time: while one is open for that repository, tell the user and start the next only after it is closed or the user asks for a second one anyway.
4. Never answer a job's permission card for the user. Background subagents surface every permission prompt in the cockpit and name the job that asks; in T3 it is an approval card in the cockpit thread. Only the user answers it, and a grant for the session covers the cockpit and every job.
5. Questions go through question cards, and the cockpit asks them as they arrive. A job cannot ask the user itself (Job 2): it writes a card, marks itself done, and ends its turn with a reply that names the card file, and its completion notification reaches the cockpit. Ask the open cards of every job that is not running right away: on that notification turn (`node <plugin>/scripts/pending.mjs list --job <job file>` lists that job's cards), and whenever the kit's hooks list them at the session's start. Read `<plugin>/skills/pending/SKILL.md` by path and do its step 2 for the cards under "To publish" and its step 3 for those under "Questions". A card of a running job is not asked. A timed-out or unanswered question leaves its card, which is asked again at the next trigger; never take an option for the user. A `question` card that asks to start another role's job is started here on yes, with step 3. On the notification, also tell the user what the job did and each choice it decided itself, from the outcome in its job file. `/tedy:pending` is the manual and recovery view of the same cards, the open jobs and the other drafts.
6. Answers and rework go through SendMessage. On a job's answered question card, `approve.reword`, a refused card or a rework request, write the note to a file and run `job.mjs resume <job file> --note-file <file>`. It appends the note to the job file as `## Note <time>`, marks the job file and its record running and prints one JSON object:
   - `"tool": "SendMessage"` when this cockpit session runs the job's agent and that agent is `idle` or `stopped`: call SendMessage with its `to` (the agent id) and `message`. The agent resumes in the background with its whole history.
   - `"tool": "Agent"` when the cockpit session that ran the job has ended, or no agent was bound and the cockpit that started the job is not alive: call the Agent tool with its other five fields. A fresh agent starts from the job file, the note included.
   It refuses and writes nothing in every case `close` refuses (step 7): while the job's agent, or any later agent its record holds, is running or waiting in a live cockpit (wait until it is idle, or stop it with TaskStop), while the job is `not started` and the cockpit that started it is alive, and when its agent is bound but its launch record holds no cockpit pid. It also refuses when another live cockpit session runs the job's agent: resume it there. `resume` acts only on the role and folder that `start` recorded in the state dir, refuses a job file that differs from that record, and refuses when the job's folder no longer exists. For a job v0.2.24 or v0.2.25 started, it refuses and writes nothing while the claude session the older kit recorded is still open (its pid and start time both match), so that session and a new agent never work the job at once (only a record that holds a claude pid can be held; v0.2.24 recorded none, nor did v0.2.25 for a job no session bound); quote the refusal and ask the user to end that session first. When the session an older kit recorded worked in a linked worktree of the job's repository (a T3 worktree of v0.2.25), every fresh Agent spec `resume` prints names that worktree as the folder to work in, because the job's branch and commits are there and not in the job file's `cwd`. Once the answer has gone back, or the job a question card asked for has started, `pending.mjs done <card>` archives the card, which stays the record under `plans/archive/` and no longer holds `close`.
7. Close: once a job is `done` or `stopped` and no open card names it, run `job.mjs close <job file>`. A runaway job, or one the user stops: call `TaskStop` with the job's agent id (the hooks mark the job `stopped` only on its exact agent id), then `job.mjs close <job file> --reason "<why>"`. `close` refuses and writes nothing while the job's agent, or any later agent its record holds under `agents`, is running or waiting in a live cockpit session (TaskStop that agent by its id), while the job is `not started` and the cockpit that started it is alive (its agent may be starting), and when its agent is bound but its launch record holds no cockpit pid (the kit cannot tell); in the last two, end that agent or the cockpit session first. A job whose Agent call never happened (a refused prompt, Esc) reads `not started` and closes once the cockpit session ends. A record that no agent bound and that holds no cockpit pid (`start` ran outside claude) closes with a line saying nothing was bound and nothing was signalled. A job v0.2.24 or v0.2.25 started (its record has no agent name) has no subagent: `close` closes it without signalling anything and says that any session it had (a T3 thread, a terminal pane or a claude session) is the user's to end, which you tell the user; `close` and `prune` keep its core worktree while the session the older kit recorded is still open; `resume` refuses while that session is still open (Cockpit 6) and once it has ended prints a fresh Agent spec for the job. Once the agent is idle or stopped, or its cockpit session has ended, it marks the job closed, turns its launch record into a closed tombstone and removes its core worktree when that has no uncommitted changes, no commit missing from the remote, no file `git ls-files -v` flags assume-unchanged or skip-worktree (git status hides an edit to such a file) and no ignored file other than a whole top-level folder git reports as ignored (`git status --ignored=matching`) whose name is `node_modules`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.turbo`, `.cache`, `coverage`, `.parcel-cache`, `.vite` or `target`. It says what it kept and why; a git command that fails while it checks the tree keeps the tree, with git's error as the reason, and the job is closed all the same. Run from inside that worktree, it keeps the tree; `prune` from elsewhere removes it later. `close` and `prune` take the worktree, its branch and its base only from the launch record `start` wrote, never from the job file, and remove a tree only while `git worktree list --porcelain` of the recorded repository lists it on the recorded branch. The tombstone keeps the job's role, file and every recorded agent with its state, so an agent of the closed job that is still about keeps its job asks; while a kept core worktree waits for `prune` it also keeps that tree, the cockpit's session and claude pid, so `prune` keeps the tree while a recorded agent runs again. `list`, `/tedy:pending` and `resume` treat a tombstone as no launch record. `close` takes no flag but `--reason`: any other, a `--reason=…` form included, is an error that writes nothing.
8. `job.mjs list` shows every open job with its age and, for a running one, `not started` until its agent's first tool event, then the state its hooks wrote: `running`, `waiting: permission`, `idle` (the agent finished its turn) or `stopped` (the cockpit's TaskStop; it stays `stopped` through the agent's later events until `resume`); `lost (cockpit gone)` once the cockpit's claude process has ended; `unknown (no cockpit pid recorded)` when the hooks could not find it. A running job v0.2.24 or v0.2.25 started shows `older kit` instead of `not started`, or `older kit (session open)` while the claude session that kit recorded still runs (only a record that holds a claude pid can show it open); the "Jobs" group of `pending.mjs list` shows the same for it, and the file status for every other job. A pid whose start time differs from the record, or that is not a claude process, is never taken for the cockpit. `job.mjs prune [--days N] [--dry-run]` removes the core worktrees of closed jobs, of done or stopped jobs whose branch is merged into `origin/<base>`, and of jobs idle more than N days (default 10), with the same checks as `close`, and keeps the worktree in every case `close` refuses: any recorded agent is running or waiting in a live cockpit (after a SendMessage `resume` too), a closed job's included, the job is `not started` while its cockpit runs, or its agent is bound and no cockpit pid was recorded. It also keeps the worktree of a job not closed whose agent is `idle` or `stopped` in a live cockpit, because SendMessage can still resume that agent.
9. Jobs end when the cockpit session ends: a background subagent lives in the session that started it. Quitting the cockpit or closing its T3 thread ends every running job, `list` then shows it `lost (cockpit gone)`, and `resume` starts a fresh agent from its job file.

## Job

1. Read the job file the prompt names, then follow the role skill the prompt names on the request in it: pm and review through the Skill tool (`tedy:pm`, `tedy:review-pr`), dev by reading the dev `SKILL.md` the prompt gives, devops with none. Read `<plugin>` and `${CLAUDE_PLUGIN_ROOT}` in kit files as the plugin root the prompt gives. A `## Note` at its end is the latest rework request. Work in the folder the job file's `cwd` names, unless the prompt names another folder to work in. Keep the files it writes for itself (card bodies, the outcome) under the project's `plans/`. Edit drafts and job files with the Edit or Write tool, never with `sed` or other shell rewrites: a shell edit of a draft that holds a publish line asks like the publish itself.
2. A job cannot ask the user: a background subagent has no AskUserQuestion. Decide every local, reversible choice yourself, the next-step menu included (the recommended next step and one alternative go into the outcome, and the job ends), and record each ruling with its reason in the outcome (step 6). Stop only for a decision the user must make: publishing under the user's name, a push or PR beyond this job's own task branch and draft PR, a merge, a scope cut, picking a side in a conflict between sources, or a destructive or irreversible step. For one of those, write a `question` card with the options and their consequences (`pending.mjs card question --job <this job file> …`), run `job.mjs done` with an outcome that names the card and what waits on it, and end the turn with a reply that names the card file. Work for another role takes a card the same way (step 4). The answer arrives as a message from the cockpit. Publish approval is not a question: it stays on a card (step 3).
3. Every write that needs the user's approval becomes a `publish` card holding the exact command, with `--job <this job file>`, and its text (`pending.mjs card publish …`); the job never runs that write. In a review job, status after merge is `merged-sweep.mjs --job <this job file>`.
4. Work for another role becomes a `question` card ("start a <role> job for …?"); the cockpit starts it on yes. A job never starts a job.
5. Local work goes ahead without a card: the worktree, commits, pushing the task branch and the draft PR with `OP#`. A dev job commits and pushes its task branch itself and never asks before committing. Run git in the job's folder (step 1) as `git -C <folder> <subcommand>`, because the agent's shell starts in the cockpit's folder, not the job's. When `git rev-parse --path-format=absolute --git-dir --git-common-dir` in that folder prints two different paths, it is already a linked worktree, the one `start` made: a dev job works there on its `branch` and skips the dev skill's own worktree step, making and removing none.
6. End every path with `node <plugin>/scripts/job.mjs done <this job file> --outcome-file <f>`, the outcome naming the drafts, cards, PR URLs, report path and each choice the job decided itself with its reason, or with `job.mjs stop <this job file> --reason "<why>"`, and make the final reply name every card file the job wrote, so the cockpit asks them on its notification turn. `stop` only marks the job stopped. A job reports only itself and never runs `job.mjs close`: the role gate asks before a literal `job.mjs close` a job runs, in every permission mode and, while the project maps parse, with the role gate off, and names the job file, and `close` refuses any job whose agent is still running, this job's own included. Accepted ceilings: `done` and `stop` take any job file and a job may edit the `status:` of any job file under `plans/`, so a job can mark another job done or stopped; a job can rewrite a launch record through a shell command or point `TEDY_STATE_DIR` elsewhere. Every job keeps the Agent tool, so a review or pm job spawns the `tedy:reviewer` lenses its skill calls for. A `tedy:reviewer` child stays under the read-only reviewer gate. A subagent a job spawns whose type is not `tedy:` is judged as the cockpit, not as the job, so the close and kit-state asks do not reach it: a job that routes work through a general subagent, deliberately or by mistake, is an accepted ceiling (ADR 0019). The kit guards against a job acting on another job by mistake; a job that deliberately attacks another job under `bypassPermissions` is beyond what a same-user hook can prevent (ADR 0019).

## Permissions

A job runs in the cockpit's permission mode, because Claude Code ignores `permissionMode` for plugin subagents: under `bypassPermissions` it runs without prompts, and in `default` mode each of its prompts waits in the cockpit (Cockpit 4), which `job.mjs list` shows as `waiting: permission`. The kit writes no settings file per role; the user's own settings apply to the cockpit and its jobs alike. The guard is the kit's hook asks (the role gate, the publish gates, git-gate's push asks) and the publish ask rules, which prompt in the cockpit in every mode. In place of the ask rules the role settings files carried, the role gate asks a job, in every mode and, while the project maps parse, with the role gate off, before any `git … --output` form and before an Edit, Write or NotebookEdit under the kit's profile dir or state dir; the cockpit is not asked. Monitor runs a command as Bash does, so every kit gate that reads a Bash command judges a Monitor command by the same rules. The user never sees a background job's transcript, so the publish-quote gate (`gates.publishQuote`) checks a job's post, reply or edit against the cockpit's main transcript, never the job's own; a body a job quoted only in its own reply does not count as shown.

Cost: each job pays its own startup context and has no spend cap. Its tool output stays out of the cockpit's context, but each completion notification enters it, so start one job per request, not one per step.
