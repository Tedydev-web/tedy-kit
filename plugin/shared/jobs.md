# Jobs (map has `jobs: true`)

In a map with `jobs: true`, the session the user types into is the cockpit, and each role request runs as its own session, a job: a T3 thread, a herdr pane, or a terminal the user starts with the command `node <plugin>/scripts/job.mjs start` prints. `<plugin>` is the plugin root. T3 and herdr are optional adapters; without them the printed command does everything. A job file is `plans/jobs/<yymmdd-hhmm>-<role>-<slug>.md` under the map's `paths[0]`, in the hand-off format: `to: tedy:<role>`, `from: cockpit`, `status`, `created`, `title`, `cwd`, and for a dev job with a repository `repo`, `branch`, `base`, `worktree` and `worktree_owner`, then the request and its sections. Its session, claude process and state live in the launch record in the state dir, written by the kit's hooks.

## Which session this is

A session whose first prompt starts with the kit's launch form for a job file, `/tedy:<skill> job "<file>"` or, for devops, `Job file "<file>"`, is that job; the path sits in double quotes with JSON escapes, so a project folder whose path holds a space or a quote binds too (its hook input carries `agent_type: tedy:<role>`). A job path anywhere else in that prompt, or in a later prompt, binds nothing. In a `jobs` map any other session is the cockpit, except a session the map still lists in `sessions`, which keeps its legacy role until the switch.

## Cockpit

1. Do no role work: read only what picking the owner needs. Tracker, PRD, Doc or Figma → `pm`; a PR review → `review`; code in a repository → `dev` with `--repo <path>`; deploy or infrastructure → `devops`. Read-only questions the cockpit may answer itself.
2. Typing a request is the user's approval to start its job. Ask one `AskUserQuestion` only when the owner is unclear or the request spans two roles, and split such a request into one job per role.
3. Write the user's words verbatim into a temporary file, followed by `## User decisions` (what the user settled, or "none yet"), `## First safe step` (one read-only step) and `## Sources` (locators). Then `node <plugin>/scripts/job.mjs start <pm|dev|review|devops> --title "<short title>" --body-file <file> [--repo <path>] [--branch <name>] [--t3] --json`, with `--t3` when your tool list has `t3_thread_launch` (`job.mjs` cannot see your tools). It writes the job file and its launch record, picks an adapter in the order t3, herdr (`HERDR_ENV=1` and `herdr` on PATH), print, and prints the launch spec: `role`, `cwd`, `title`, `agent`, `settings`, `prompt`, `via`, `command`, plus `t3` or `herdr`. `--via t3|herdr|print` forces an adapter; one that cannot run is an error naming why. Then by `via`:
   - `t3`: call `t3_thread_launch` with the T3 project whose folder holds `spec.cwd` (for a resume whose `workspaceStrategy` is `existing_worktree`, the project whose folder is the job file's `repo`), `title: spec.t3.title`, `modelSelection.instanceId: spec.t3.instanceId`, `message: spec.t3.message`, and `workspaceStrategy: spec.t3.workspaceStrategy` when it is set. The typed request is the user asking for this new thread. When the call fails or `orchestrator_capabilities` does not list the instance `tedy-<role>`, fall back to print, then offer once to add the instances: one `AskUserQuestion`, header `t3.header`, whose option `t3.write` names the file it changes, `~/.t3/userdata/settings.json`, and says it is backed up first and gets `tedy-pm`, `tedy-dev`, `tedy-review` and `tedy-devops`, with `t3.skip` beside it. That file is outside the profile, so it is written only on this yes. On yes run `job.mjs t3-instance --all --write`, quote what it prints (the backup, each instance added, updated or unchanged), and check that `orchestrator_capabilities` now lists the instances, since T3 loads the file without a restart. A refusal (the file is missing, is not JSON, or has no `providerInstances` object) is quoted as it is and the job stays on print. The instances carry only Launch arguments, `--agent tedy:<role> --settings <file>`; the settings file holds the `TEDY_*` env. `job.mjs t3-instance <role>` without `--write` prints them for a user who would rather paste them into T3 Settings > Providers. Without T3 none of this runs.
   - `herdr`: `job.mjs` has already opened a tab with `herdr tab create` (or, for a dev job, `herdr worktree create`) and run `herdr agent start <role>-<hash> --kind claude --pane <id> -- --agent tedy:<role> --settings <file> <prompt>` in it; reply with the agent name and pane. A `warning:` that the agent waits at a prompt (the trust dialog, say) means the user answers it in that pane. Any other herdr failure prints a warning and the command, as print.
   - `print`: reply with the job name, its file and `spec.command`, `cd '<cwd>' && claude --agent tedy:<role> --settings '<file>' '<prompt>'`, for the user to run in any terminal.
   Never run that command in the cockpit's own Bash: a session started there lives in the cockpit's process and dies with it, and nobody sees its prompts.
   A dev job with `--repo` works in its own worktree, on `--branch` (default `feat/<title slug>`) from the map's integration branch (the repo's `branch`, else `origin/HEAD`). The adapter that launches it owns it: T3 makes it from `workspaceStrategy` and deletes it on merge, after 10 days or with the thread; herdr makes it with `herdr worktree create --cwd <repo> --branch <branch> --base origin/<base> --no-focus`; print makes it with `git worktree add` under `<repo parent>/.worktrees`, or the map's `worktree_root`.
4. The folder a job starts in must be trusted once; the trust dialog shows in the job's own window.
5. Approve with `/tedy:pending`: it lists the cards and the jobs that are not closed. A card of a running job is not offered. A `question` card that asks to start another role's job is started here on yes.
6. Rework: on `approve.reword`, a refused card, or an answer the job needs, write the note to a file and run `job.mjs resume <job file> --note-file <file>`. It appends the note to the job file and prints a `claude --resume <session> --agent tedy:<role> --settings '<file>' '<note prompt>'` command for the user; the note prompt starts with the job's own launch form, with the note after it, so a note that names another job does not bind the session to that job. When the job's session is still open it refuses before it opens a tab or starts anything, with every adapter: the user types the note in that open thread or pane, or closes that session first, because resuming a running session would start a second claude on it that the kit loses track of. The resumed session starts in the folder the job's session ran in, which the hooks record as `session_cwd` when they bind it (for a T3-owned dev job, T3's worktree), else in the job's recorded `cwd`; `session_cwd` never replaces `cwd`. `resume` takes `--t3` and `--via` like `start`: inside herdr it opens a new tab and agent; with `--t3` its spec's `t3` is a new thread whose message is the note prompt, for when the job's thread is gone; when the folder it resumes in is a linked worktree other than the job's `repo` (T3's worktree of a T3-owned dev job, or a core or herdr worktree), `spec.t3.workspaceStrategy` is `{ "type": "existing_worktree", "worktreePath": <that folder> }`, which the cockpit passes to `t3_thread_launch` as in step 3, because T3 reads neither `spec.cwd` nor the command. While the job's T3 thread is open, the user types the note there instead.
7. Close: once a job is `done` or `stopped` and no open card names it, `job.mjs close <job file>` ends the job's claude process (SIGTERM, SIGKILL after 5 s) when it is still the recorded one, marks the job closed and deletes its launch record; transcripts stay. `/tedy:pending` runs it as `job.mjs close <job file> --if-ended`, which refuses and writes nothing while the recorded session is still open, so the cockpit closes a finished job only after its session has ended and otherwise tells the user it is still open; a job's `done` or `stopped` may have been written by another job (Job 6). `close` is the only command that signals a job's process; `stop` only writes the job's stopped status. When the process runs as another user (EPERM), `close` says so and leaves the job not closed. For a job no session has bound yet it says that nothing was signalled and that a session started later from its printed command, T3 thread or herdr pane is not tracked as the job. Once that session has ended, `close` closes the herdr pane the kit opened for the job; with no pid recorded it cannot tell that the session has ended, so it keeps the pane, as it does while the session still runs, and says which. It closes it (`herdr pane close <pane>`) only when `herdr pane get` reports exactly the job's recorded session in it: a pane the command runs in, one that reports a different session, and one that reports no session stay open, and `close` says which, and a herdr failure is only a warning. It also removes the job's core worktree when that has no uncommitted changes, no commit missing from the remote, no file `git ls-files -v` flags assume-unchanged or skip-worktree (git status hides an edit to such a file) and no ignored file other than a whole top-level folder git reports as ignored (`git status --ignored=matching`) whose name is `node_modules`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.turbo`, `.cache`, `coverage`, `.parcel-cache`, `.vite` or `target`; an ignored file inside a tracked `build` folder, or in a `build` or `out` folder nested below the top level, keeps the tree. It says what it kept and why, naming those ignored files; a git command that fails while it checks the tree keeps the tree, with git's error as the reason, and the job is closed all the same. Run from inside that worktree, it keeps the tree and says so; `prune` from elsewhere removes it later. The hooks never bind a session to a job file whose status is `closed`, so a closed job's session that still runs is not tracked as that job again. A runaway job: `job.mjs close <job file> --reason "<why>"`. `job.mjs list` shows every open job with its age and, for a running one, `not started` until the user runs its command, then the state its main thread's hooks wrote (`running`, `waiting: permission`, `waiting: input`, `waiting: question`, `idle`; a subagent's events never change it), or `lost (last seen <time>)` once its claude process is gone, or `lost (no pid recorded, started by an older kit)` for a job whose record has a session but neither a pid nor a binding time, or `unknown (no pid recorded)` for a bound session whose claude process the hooks could not find. For a job herdr runs it adds herdr's own state, as in `running (herdr: blocked)`; a kit `waiting` or `lost` state is shown alone. `job.mjs prune [--days N] [--dry-run]` removes the core worktrees of closed jobs, of done or stopped jobs whose branch is merged into `origin/<base>`, and of jobs idle more than N days (default 10, as T3). It keeps a worktree whose session is open, that has uncommitted changes, that has commits on no remote, that has a file flagged assume-unchanged or skip-worktree, or that holds such an ignored file, and prints why. T3 and herdr worktrees are left to their owner. `close` and `prune` take the worktree, its owner, its branch and its base only from the launch record `start` wrote, never from the job file, so an edited job file cannot point them at another tree, and they remove a tree only while `git worktree list --porcelain` of the recorded repository lists it on the recorded branch; a tree `close` keeps keeps its record, without the session, until `prune` removes it. `resume` acts only on the role, folder and mode that `start` recorded in the state dir, refuses a job file that differs from that record, and passes the role's settings file, written afresh, never a settings path from the record. A pid whose start time differs from the record, or that is not a claude process (its `comm` or the first word of its command line is `claude`), is never signalled, and `list`, `resume` and `prune` do not take it for the job's session.
8. The job's prompts are the user's to answer in the job's own window: its permission prompts and its questions. The cockpit never answers them. T3 shows them as the thread's needs-input state; inside herdr the job's hook also raises a herdr notification when it starts waiting.

## Job

1. Read the job file the prompt names, then follow the role skill (`/tedy:pm`, `/tedy:dev`, `/tedy:review-pr`; devops has none) on the request in it. A `## Note` at its end is the latest rework request. Keep the files it writes for itself (card bodies, the outcome) under the project's `plans/`, which its allowlist lets it write without a prompt. Edit drafts and job files with the Edit or Write tool, never with `sed` or other shell rewrites: a shell edit of a draft that holds a publish line asks like the publish itself.
2. Ask the user with `AskUserQuestion` in this window when a decision is needed, the next-step menu included; the user answers here. Publish approval is not a question: it stays on a card (step 3).
3. Every write that needs the user's approval becomes a `publish` card holding the exact command, with `--job <this job file>`, and its text (`pending.mjs card publish …`); the job never runs that write. In a review job, status after merge is `merged-sweep.mjs --inbox --job <this job file>`.
4. Work for another role becomes a `question` card ("start a <role> job for …?"); the cockpit starts it on yes. A job never starts a job.
5. Local work goes ahead without a card: the worktree, commits, pushing the task branch and the draft PR with `OP#`. A dev job commits and pushes its task branch itself and never asks before committing. Run git in the job's worktree as `git -C <worktree> <subcommand>`, never `cd <worktree> && git …`, so the job's allowlist covers it. When `git rev-parse --path-format=absolute --git-dir --git-common-dir` in the job's folder prints two different paths, the folder is already a linked worktree, the one the job was started in: a dev job works there on its `branch` and skips the dev skill's own worktree step, making and removing none. In a job whose file has `worktree_owner: t3` or `herdr`, push the branch with `git push -u origin <branch>` right after the first commit, unless the user asked for a report only, because T3 deletes its worktrees after 10 days; the draft PR still waits for the dev skill's step 8.
6. End every path with `node <plugin>/scripts/job.mjs done <this job file> --outcome-file <f>`, the outcome naming the drafts, cards, PR URLs and report path, or with `job.mjs stop <this job file> --reason "<why>"`. `stop` only marks the job stopped: it signals no process, and its session stays open for the user. A job reports only itself. That is this doc's instruction, not a guarantee: `done` and `stop` take any job file, and a job may edit the `status:` of any job file under `plans/`, so a job can mark another job done or stopped; the cockpit therefore closes a finished job only after its session has ended (Cockpit 7). A job never runs `job.mjs close`, which is on no role's allowlist and ends a session. `close` itself refuses to run in a job's session: it walks up from its caller through every ancestor process to pid 1, and when the pid and start time of any one of them are the ones a launch record holds, it stops before it writes anything, for any job, its own included, and says to ask the user to close the job from the cockpit. Every way of running it while the job's claude process is still one of its ancestors gets that refusal: a variable or `$(…)` as the subcommand, a symlink to the script, `xargs`, a script file, a shell run under a link named `claude`, a nested `claude` session the job starts, `claude --resume` of the job's own session included, since the hooks replace a record's claude pid only once the recorded claude has ended. On top of that the role gate asks before a literal `job.mjs close` a job runs, in every permission mode and with the role gate off, and names the job file; the cockpit is not asked. Neither sees a process the job detaches from its claude process tree (the job's claude is then no ancestor of it), a session before its first hook binds it, a launch record the job rewrote first, a `TEDY_STATE_DIR` the job points at another folder for the command (`close` then finds no record of the caller and none of the target, so it marks the target file closed and signals nothing; with a copied state dir that lacks only the caller's record it closes fully), a plain `kill`, `herdr pane close <pane>` or `herdr agent stop <name>` run from a job, or a job that marks another job `done` or `stopped`. These are accepted ceilings: the kit guards against a job acting on another job by mistake, and a job that deliberately attacks another job under `bypassPermissions` is beyond what a same-user hook can prevent (ADR 0018, Threat model). The role gate asks the same way before a job runs `job.mjs t3-instance --write`, which only the cockpit runs after the user's yes. `job.mjs start` and `resume` run from a job are not asked: "a job never starts a job" (step 4) is a rule of this doc, not a gate.

## Permissions

A job runs in the user's own default permission mode from their settings (usually `bypassPermissions`), the mode a cockpit started without a mode flag also runs in; `job.mjs start` adds `--permission-mode` to the command only when it is given one. The guard is the kit's hook asks (the role gate, the publish gates, git-gate's push asks) and the publish ask rules, which prompt in the job's window in every mode. The allowlist below matters only to a user whose mode is `default`, and there a job can stop on any command outside it: a dev job in `default` mode waited on a permission prompt at its first Bash call, a read of its job file. `job.mjs list` shows such a job as `waiting: permission`.

`job.mjs settings <role>` writes the role's settings file, `<state>/jobs/settings/<role>.json`, and `start` writes it again before it prints the command that passes it with `--settings`. It holds the role's allowlist for every map with `jobs: true`, the ask rules, and the `TEDY_STATE_DIR` and `TEDY_PROFILE_DIR` env when they are set. Every role may read the plugin, the project and the profile, write under `plans/`, run the kit's read scripts, `pending.mjs card publish|question|notify`, `job.mjs done|stop`, and the read-only git and `gh pr` commands. Dev and devops jobs may also edit, run `npm test` and the `npm run` scripts `typecheck`, `lint`, `lint:check`, `format:check`, `check`, `test`, `test:unit` and `test:cov`, make and remove worktrees, commit, push with `git push -u origin <branch>` and open a draft PR. Review jobs may also run `npm test` and add a worktree. Publish scripts, deploys, `job.mjs start` and `pending.mjs done` are not on any list, and the kit's publish ask rules and its gates' asks prompt over every allow rule. Every role also gets the ask rule `Bash(git *--output*)`, because `git diff` and `git log` write a file through `--output`, and an ask rule for edits of the profile and the state dir, maps included. Under `bypassPermissions` the allow list changes nothing; a job can still write the state dir and the maps through a shell command there, and the kit's hook asks are the guard.

Cost: a job session has no spend cap, and each start pays its startup context (about 125k cache-write tokens on the user's setup, measured 2026-11-06), so start one job per request, not one per step.
