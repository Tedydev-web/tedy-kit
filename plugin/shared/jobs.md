# Jobs (map has `jobs: true`)

In a map with `jobs: true`, the session the user types into is the cockpit, and each role request runs as its own session, a job, which the user starts with the command `node <plugin>/scripts/job.mjs start` prints. `<plugin>` is the plugin root. A job file is `plans/jobs/<yymmdd-hhmm>-<role>-<slug>.md` under the map's `paths[0]`, in the hand-off format: `to: tedy:<role>`, `from: cockpit`, `status`, `created`, `title`, `cwd`, then the request and its sections. Its session, claude process and state live in the launch record in the state dir, written by the kit's hooks.

## Which session this is

A session whose first prompt names a job file is that job (its hook input carries `agent_type: tedy:<role>`). In a `jobs` map any other session is the cockpit, except a session the map still lists in `sessions`, which keeps its legacy role until the switch.

## Cockpit

1. Do no role work: read only what picking the owner needs. Tracker, PRD, Doc or Figma → `pm`; a PR review → `review`; code in a repository → `dev` with `--repo <path>`; deploy or infrastructure → `devops`. Read-only questions the cockpit may answer itself.
2. Typing a request is the user's approval to start its job. Ask one `AskUserQuestion` only when the owner is unclear or the request spans two roles, and split such a request into one job per role.
3. Write the user's words verbatim into a temporary file, followed by `## User decisions` (what the user settled, or "none yet"), `## First safe step` (one read-only step) and `## Sources` (locators). Then `node <plugin>/scripts/job.mjs start <pm|dev|review|devops> --title "<short title>" --body-file <file> [--repo <path>]`. It writes the job file and its launch record and prints one command, `cd '<cwd>' && claude --agent tedy:<role> --settings '<file>' '<prompt>'`; `--json` prints the launch spec (`role`, `cwd`, `title`, `agent`, `settings`, `prompt`, `command`). Reply with the job name, its file and that command, for the user to run in any terminal. Never run it in the cockpit's own Bash: a session started there lives in the cockpit's process and dies with it, and nobody sees its prompts.
4. The folder a job starts in must be trusted once; the trust dialog shows in the job's own window.
5. Approve with `/tedy:pending`: it lists the cards and the jobs that are not closed. A card of a running job is not offered. A `question` card that asks to start another role's job is started here on yes.
6. Rework: on `approve.reword`, a refused card, or an answer the job needs, write the note to a file and run `job.mjs resume <job file> --note-file <file>`. It appends the note to the job file and prints a `claude --resume <session> --agent tedy:<role> --settings '<file>' '<note prompt>'` command for the user. When the job's session is still open it warns: the user types the note in that window instead, or ends the session first, because resuming a running session starts a copy.
7. Close: once a job is `done` or `stopped` and no open card names it, `job.mjs close <job file>` ends the job's claude process (SIGTERM, SIGKILL after 5 s) when it is still the recorded one, marks the job closed and deletes its launch record; transcripts stay. A runaway job: `job.mjs close <job file> --reason "<why>"`. `job.mjs list` shows every open job with its age and, for a running one, `not started` until the user runs its command, then the state its hooks wrote (`running`, `waiting: permission`, `waiting: input`, `waiting: question`, `idle`), or `lost (last seen <time>)` once its claude process is gone, or `lost (no pid recorded, started by an older kit)` for a job whose record has a session but neither a pid nor a binding time. `resume` acts only on the role, folder and mode that `start` recorded in the state dir, and refuses a job file that differs from that record. A pid whose start time differs from the record is never signalled.
8. The job's prompts are the user's to answer in the job's own window: its permission prompts and its questions. The cockpit never answers them.

## Job

1. Read the job file the prompt names, then follow the role skill (`/tedy:pm`, `/tedy:dev`, `/tedy:review-pr`; devops has none) on the request in it. A `## Note` at its end is the latest rework request. Keep the files it writes for itself (card bodies, the outcome) under the project's `plans/`, which its allowlist lets it write without a prompt.
2. Ask the user with `AskUserQuestion` in this window when a decision is needed, the next-step menu included; the user answers here. Publish approval is not a question: it stays on a card (step 3).
3. Every write that needs the user's approval becomes a `publish` card holding the exact command, with `--job <this job file>`, and its text (`pending.mjs card publish …`); the job never runs that write. In a review job, status after merge is `merged-sweep.mjs --inbox --job <this job file>`.
4. Work for another role becomes a `question` card ("start a <role> job for …?"); the cockpit starts it on yes. A job never starts a job.
5. Local work goes ahead without a card: the worktree, commits, pushing the task branch and the draft PR with `OP#`. A dev job commits and pushes its task branch itself and never asks before committing. Run git in the job's worktree as `git -C <worktree> <subcommand>`, never `cd <worktree> && git …`, so the job's allowlist covers it.
6. End every path with `node <plugin>/scripts/job.mjs done <this job file> --outcome-file <f>`, the outcome naming the drafts, cards, PR URLs and report path, or with `job.mjs stop <this job file> --reason "<why>"`. Run from the job itself, `stop` marks the job stopped and leaves its own session open for the user.

## Permissions

A job runs in the user's own default permission mode from their settings (usually `bypassPermissions`), the mode a cockpit started without a mode flag also runs in; `job.mjs start` adds `--permission-mode` to the command only when it is given one. The guard is the kit's hook asks (the role gate, the publish gates, git-gate's push asks) and the publish ask rules, which prompt in the job's window in every mode. The allowlist below matters only to a user whose mode is `default`, and there a job can stop on any command outside it: a dev job in `default` mode waited on a permission prompt at its first Bash call, a read of its job file. `job.mjs list` shows such a job as `waiting: permission`.

`job.mjs settings <role>` writes the role's settings file, `<state>/jobs/settings/<role>.json`, and `start` writes it again before it prints the command that passes it with `--settings`. It holds the role's allowlist for every map with `jobs: true`, the ask rules, and the `TEDY_STATE_DIR` and `TEDY_PROFILE_DIR` env when they are set. Every role may read the plugin, the project and the profile, write under `plans/`, run the kit's read scripts, `pending.mjs card publish|question|notify`, `job.mjs done|stop`, and the read-only git and `gh pr` commands. Dev and devops jobs may also edit, run `npm test` and the `npm run` scripts `typecheck`, `lint`, `lint:check`, `format:check`, `check`, `test`, `test:unit` and `test:cov`, make and remove worktrees, commit, push with `git push -u origin <branch>` and open a draft PR. Review jobs may also run `npm test` and add a worktree. Publish scripts, deploys, `job.mjs start` and `pending.mjs done` are not on any list, and the kit's publish ask rules and its gates' asks prompt over every allow rule. Every role also gets the ask rule `Bash(git *--output*)`, because `git diff` and `git log` write a file through `--output`, and an ask rule for edits of the profile and the state dir, maps included. Under `bypassPermissions` the allow list changes nothing; a job can still write the state dir and the maps through a shell command there, and the kit's hook asks are the guard.

Cost: a job session has no spend cap, and each start pays its startup context (about 125k cache-write tokens on the user's setup, measured 2026-11-06), so start one job per request, not one per step.
