The canon and the knowledge base

Two things live here. The knowledge base is the store of best practices gathered from open source, docs, the community and experts, meant for building anything; agents read it before they design. The canon is the narrower set of rules the kit itself is built by, with the tests that hold each rule; it runs whenever npm test runs in this repository. Neither is a skill or a command.

The canon

The three parts

Rules

docs/canon/standard.json

The versioned standard. Each rule gives its reason, its class (a platform fact, your policy, or a gap in the model) and what enforces it: a test named by file and exact title, or review with a stated reason why no machine can check it. Its history records why each version exists.

Register

docs/canon/conformance.json

Every skill, ADR, prior-art card and sweep record, with the standard version it meets. An artifact is judged only by rules that existed at its version, so a new rule never fails an old ADR. A new artifact must be registered at the current version.

Knowledge base

docs/prior-art/index.md

Everything learned from open source, docs, the community and experts, indexed by domain with a "use when" line per entry. Cards are GitHub sources read at file:line; notes are findings from posts, videos, docs and reports. Notes start private on your machine and are published one at a time. Read it before designing anything.

Two measuring tools sit beside them: the inventory of Claude Code surfaces the kit's needs are judged against (claude-code-inventory.json, surface-fit.json), and the pressure evals in plugin/evals/pressure/, whose baseline.json keeps each scenario's pass rate and cost per model. The decisions behind all of it are ADR 0011, 0013 and 0014.

What happens when someone changes the kit

The change is made

Usually by an agent working on the kit: a skill edit, a new hook, an ADR, a card.

npm test runs the canon checks

Examples: a SKILL.md over 9,000 characters; skill descriptions over the always-on budget; a skill that pins model:; a hook on an event that speaks every turn; an artifact missing from the register; an ADR without its prior-art section; a feat or fix commit without an ADR: trailer; a dead link in the docs; a manifest version that does not match the release tag.

Red means the change does not go in as is

Either the change is fixed, or the rule itself changes. A rule changes only with a new standard version and a history entry that records your approval.

Behaviour and cost are measured when it matters

After a model or Claude Code update, or a change meant to save tokens, the pressure evals run and rebaseline.mjs compares them with the baseline: it refuses a lower pass rate on a kit arm, and a cost rise past the cell's measured noise, unless you accept it.

Scope

QuestionAnswer
Does it check my project repositories?No. Only the tedy-kit repository. Your projects are untouched.
Does it change how the skills behave?Not directly. It holds decisions in place. The ones you notice came out of it, for example the reviewer running on claude-sonnet-5-5 without your CLAUDE.md.
Does it run on its own?Only through npm test. The repository has no CI test run, so a change made without running the tests is not checked.
Does it cost money?npm test is free and offline. Only the pressure evals spend, and each batch starts with a one-run cost check.

When you use it

SituationWhat to do
You ask an agent to change the kitNothing extra. The agent runs npm test before committing; a red canon test stops the change.
You want a new rule ("every skill must…")Ask for a rule in standard.json with its test. The agent raises the standard version, records the trigger and asks you to approve.
You plan a new skill or roleAsk the agent to read docs/prior-art/ first and cite the cards it relies on; the ADR for it must carry a prior-art section anyway.
Claude Code or the model changesA minor Claude Code release turns the inventory test red: refresh the inventory and re-judge the surface fit. A model change: run the pressure evals and rebaseline.

Known limits

  • No CI runs npm test, so the canon holds only when the tests are run.
  • Six rules are enforced by review, not by a test; each says why in whyNotMachine.
  • Four registry problems are held only in part, as designed: S16 (probes after a Claude Code update), S24 (spend logged), S25 (your approval recorded, not enforced) and S31 (the ablation proposes, never fails).
  • Eval verdicts rest on five runs an arm, which cannot tell 5 of 5 from 4 of 5.
