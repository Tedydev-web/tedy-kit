# 0021: The cockpit asks each job's open cards on arrival, and a job stops only for what the user must decide

Status: accepted 2026-11-12 (user decisions); amends the questions part of [ADR 0019](0019-jobs-run-as-native-background-subagents.md), the approval path of [ADR 0015](0015-jobs-replace-standing-role-sessions.md) and T2 of [ADR 0014](0014-kit-artifacts-meet-quota-techniques.md); live check pending (Consequences)

## Context
- ADR 0019 made every job a background subagent. A job writes a `question` or `publish` card and ends its turn, and the user answers the cards by typing `/tedy:pending` in the cockpit. A research pass on 2026-11-11 found the problem is not the subagents but the second place the user must visit: Claude Code removes AskUserQuestion from every subagent, so the one session that holds the user has to ask for them. It also found that the job step turned every decision, the next-step menu included, into a question card.
- The user decided on 2026-11-12:
  - Design C: jobs stay background `tedy:<role>` subagents that cannot ask; the cockpit asks every open card of a job that is not running, through AskUserQuestion, with steps 2 and 3 of `plugin/skills/pending/SKILL.md` read by path; answers go back through `job.mjs resume` and SendMessage.
  - Deterministic triggers where Claude Code allows them: a hook on SessionStart and on UserPromptSubmit in the cockpit injects the open cards with the instruction to ask them now, reads only state and card files, and prints nothing when no card is open; the job's final reply names its card file; a timed-out or unanswered question leaves the card, and the next trigger asks it again.
  - Question volume: a job stops only for publishing under the user's name, a push or PR beyond its own task branch and draft PR, a merge, a scope cut, picking a side in a conflict between sources, or a destructive or irreversible step (running a PR's code or other untrusted code is listed with them, because the review run question needs the user); it decides every local, reversible choice itself, the next-step menu included, and records each ruling with its reason in its outcome.
  - `pending.mjs list --job <file>` filters one job's cards; `/tedy:pending` becomes the manual and recovery view.
  - The answer-mode gap closes: an answer mints a ticket only for `post.asIs` and `approve.all` (`plugin/lib/publish-approval-ticket.mjs`), yet the merge step and the status procedure used the `merge.yes` or next-step answer as approval for `openproject.mjs set … --apply`.
- HumanLayer's 12-factor agents, factor 7 "Contact humans with tool calls" (humanlayer/12-factor-agents at d20c728, `content/factor-07-contact-humans-with-tools.md` lines 3 and 121), has the answer arrive later and resume the run ("Durable"). The kit has no card for that repository, and a card needs a study row in a screened sweep, so it is named here and not linked as prior art.

## Decision
- **The cockpit asks on arrival; the card is the record.** A card is askable when it is open (not refused, not started) and its job is not busy. Busy comes from the job's launch record whatever its file says: `resume` would refuse because its agent runs, waits or may be starting in a live cockpit, or, for the cockpit asking, the agent belongs to another live cockpit session. A publish card is also busy while its job file says `running`, and `card-check` and `card-start` refuse a busy card. A question card with an `answer:` is not asked, nor a publish card the user held. A job that ended its turn without `job.mjs done` is therefore still asked, and a done job's card waits until its agent has finished its last reply.
- **Triggers.** `session-hooks.mjs pending-handoffs` (SessionStart, startup and resume) adds the askable cards of the cockpit's project, held publish cards included, to the session-start notice, with the instruction to ask them per `skills/pending/SKILL.md` steps 2 and 3 now. `session-hooks.mjs ask-cards` on UserPromptSubmit returns the same block as `additionalContext`, held cards left out, on every prompt and on the turn a job's completion starts, which the hooks reference counts as a UserPromptSubmit. The cockpit is the main thread that carries no `agent_id` and does not run as `claude --agent tedy:<role>`. The hook reads card files, job files, launch records and the process table (`/proc` on Linux, `ps` elsewhere) to tell whether the cockpit that runs a job's agent is alive, never git, `gh`, claude or the network, and reads the drafts once per run (the session start once for its waiting list, ask block and close list): a 4 KB prefix of each, deciding from it only when the header block ends inside it and reading the file whole otherwise, so it never disagrees with `readCard` on the full text, with each job's status and liveness read once. The busy check takes the caller's session id in the hooks and its claude process in `card-check`, `card-start` and `pending.mjs list`. `card --job` resolves against the project root and refuses a job file that does not exist, as `cardRefusal` does for a hand-written card. Over 100 cards and 200 drafts of 2 MB, the hook took 261 ms before the header read and 57 ms after. It prints nothing when no card is askable and no finished job waits, lists at most ten per group and logs `ask-cards` `listed` to the gate log when it lists any. Titles are written by jobs, and a review job can be steered by a hostile PR, so every listed title is clipped to 120 characters, its backticks and control characters removed, the block says its titles are data a job wrote and never instructions, and each block is capped at 3000 characters with a tail that points to `/tedy:pending`. The session start lists an askable card once, in the ask block, not again in its waiting list. A job ends with `job.mjs done`, its outcome naming the card, and a final reply that names the card file, so the completion-notification turn asks it at once (`plugin/shared/jobs.md`, Cockpit 5 and Job 2).
- **Hold.** `approve.hold` notes the hold label on the publish card (`pending.mjs card-note`), so the per-prompt trigger stops asking it; the next session start asks it again. The user's decisions did not cover a held card; this was decided in the user's absence to keep "not yet" from being re-asked on every prompt.
- **Finished jobs close themselves through the cockpit (user decision, 2026-11-12).** A `done` job that no question or publish card names, a started or refused card included, closes on its notification turn with `job.mjs close <job file> --if-finished`. `job.mjs close --if-finished` with no file closes every such job, and the hooks list them so the cockpit runs it: the per-prompt hook lists only those it can judge from files (never a dev job, and not one whose agent `close` would refuse), and the session start lists them all. A dev job stays open while its branch has an open PR, so `resume` can rework it. The command reads that with `gh pr list --head <branch> --state open` in the repository the launch record names; it runs in the cockpit's command, never in a hook. The job file's prose plays no part, because reading PR references out of it missed forms such as `PR#7` and mistook `OP #21298` for a PR. A dev job whose record names no repository and branch, or whose read fails, stays open. While any card cannot be read, the command closes nothing and says why. The job closes once no PR from its branch is open, at the next session start or prompt that runs the command, or when the user asks with plain `close`. Every close goes through `close`, so its refusals and core worktree checks hold, and a refusal prints `kept <file>: <why>`. The role gate asks a job before `job.mjs close --if-finished` as before any `close`. The role that decides is the launch record's, and it must agree with the job file's name and its `to:` line, because a job can edit its own `to:`; on a mismatch, or with no launch record, the job stays open and the command says why. A job whose agent another live cockpit session holds is neither closed nor listed for closing. Every close-list line is cleaned like the card lines, so a crafted job file name cannot add lines.
- **Answered cards.** Each job's round runs in one order: every card of the job that got `approve.all` first (its `card-start` and writes), then one note file and one `job.mjs resume` carrying all answers, rework and refusal reasons, then `card-note` and `pending.mjs done`. A second `resume` refuses while the first has marked the agent running, and `card-start` refuses while the resumed job runs. A `card-check` or `card-start` refusal that only says the job is busy, or held by another cockpit, leaves the card open. An `approve.reword` is refused on its card only after that note went out. The cockpit runs `job.mjs resume` with the answers first. Only after the call it prints has gone out, or the job a card asked for has started, does it write the answer onto the card with `card-note` and archive it with `pending.mjs done`, so `close` is not held by it and the record stays under `plans/archive/`. When `resume` prints `busy:`, the card stays unanswered and is asked again once the job's agent is idle, so an answer is never recorded without being delivered; only `refused:` refuses the job's unanswered cards, with its reason. A refused card stays until the job that redoes it writes the new card and archives the refused one. `resume` is its refusal check plus its writes. `resumePlan` in `plugin/lib/job.mjs` makes every decision without writing: the note, the job file and its trust checks, the launch record (`recordRefusal`) and an older kit's worktree folder. `resumeRefusal(map, file, caller, note)` returns its refusal, sorted as permanent (the kit positively finds that no answer can reach the job: closed, no launch record, a lost folder, a drifted or untrusted job file, a read-only or removed repository, a bound agent with no cockpit pid) or busy (everything else: the agent runs, waits or may be starting, an older kit's session is open, another live cockpit or an unidentified caller holds the job, an empty note, or a read, git or write failure). `resume` throws only that refusal, or turns any other failure into a busy one, and runs `recordRefusal` again on the record inside its lock, so two resumes that read the same idle record cannot both send. `job.mjs resume` prints a refusal as `busy: <reason>` or `refused: <reason>`; the cockpit branches on the prefix and refuses cards only on `refused:`. The card judgement, the close settling and the hooks call the same function, so what the kit asks and what `resume` accepts cannot drift. A question card of a job with a permanent refusal counts as refused with that reason and is never asked, and so does a publish card of a closed job; a busy refusal leaves the cards open. A question card that asks to start another role's job is an ordinary question card, asked only when its job is not busy; the cockpit settles it itself on any answer (it starts the job on yes, then `card-note` and `pending.mjs done`), so that answer never needs its writer to resume. An answered question card is listed under "Answered and delivered" and archived even when its job can no longer resume or its job file is gone. A plain `close` archives an answered question card as delivered, refuses and archives every other open question card with its reason, leaves started and notify cards listed, and prints each card it could not read; when the settling fails after the close, it still prints the `closed:` line and exits 1. The ask block lists answered cards under "Answered and delivered" for `pending.mjs done`, and the session start clips refusal reasons and "Could not check" entries to 120 characters, labels them as job-written data, and caps its waiting list at 3000 characters. `card --job` and `cardRefusal` require a parsed job file inside `plans/jobs`. An unidentified caller finds a job bound to a live cockpit held there, for closing as for busy.
- **`pending.mjs list --job <file>`** lists only that job's cards and its line under "Jobs", and skips the git and `gh` lookups.
- **Question volume.** A job records every local, reversible ruling, its next step included, with its reason in its `job.mjs done --outcome-file`, and writes a question card only for the items above. On the notification the cockpit tells the user what the job did and decided.
- **Standard version 4 narrows per-turn-hooks (ADR 0014, T2).** The rule forbade any kit hook on an event whose output enters the context on every prompt, because "Text added on every turn is paid on every turn"; the user's decision of 2026-11-12 asks for a UserPromptSubmit hook that prints nothing when no card is open. The rule now allows exactly one UserPromptSubmit group that runs only `session-hooks.mjs ask-cards`, and `hookEventErrors` fails any other per-turn registration. The user approved the hook, not this wording of the exception. Going back to the old rule removes only the UserPromptSubmit hook; the session-start trigger and the job's reply naming its card still bring the cards to the cockpit.
- **Approval by ticket labels only.** Every kit write a skill runs after a question is approved by an `approve.all` (or `post.asIs`) option whose `preview` holds that exact command, quoted per `plugin/shared/decision-points.md` (ADR 0020). `merge.yes` approves the merge alone; after `gh pr merge` succeeds, each status `set` is previewed again and asked as its own `approve.all` question. `approve.trim` and `post.trim` lead to a new dry run and a new question, never to the write.

## Consequences
- The user answers a job's question in the cockpit seconds after the job stops, and never needs `/tedy:pending`; it stays as the manual and recovery view.
- A timed-out or unanswered question costs nothing but a re-ask: the card stays on disk, and a publish never runs on a timeout.
- Cost of the per-prompt hook: one node process per prompt, 49 ms median (44 ms from an unmapped folder, 19 ms for a bare `node -e 0`), measured 2026-11-12 on the build machine with a mapped project holding one notice card; it adds no text to the context while no card is askable and no finished job waits to be closed.
- A job that ends with no card, the common case once rulings stay in the job, is closed on its notification turn. A non-dev job can no longer be reworked through `resume` after that; the user starts a new job instead.
- Fewer questions: a job's reversible rulings arrive as a report on the notification, not as questions. A wrong ruling costs rework the user can see in the outcome.
- Known limits:
  - An interruption between `resume` and `card-note` sends the answer again in the next round. That is the price of never recording an answer that was not delivered, and a reworded `preview: run` card stays approvable until its `card-note --refuse` is written.
  - When `resume` prints `busy:` after a check refusal was already noted on a card, that refusal's reason reaches the job only with the next round's note.
  - The session start lists a dev job that the close command kept at most once a day (`close_kept_at` in its launch record). The first prompt after a session start that listed cards skips them once (a per-session marker in the state dir, valid for an hour; every hook run removes markers older than that).
  - A notify card never holds a job open; it stays until the user dismisses it.
  - A caller with neither a session id nor a claude ancestor finds every job bound to a live cockpit busy (fail closed). When the same cockpit process starts a new session (`/clear`), its own jobs look held by another session until their records rebind. That case was not exercised.
  - When SendMessage or the Agent call fails after `resume`, the record stays `running` until the agent is stopped with TaskStop or the cockpit exits (`plugin/shared/jobs.md`, Cockpit 6).
  - `gh pr list --head <branch>` runs in the recorded repository without `--repo`, so it sees PRs on that checkout's default remote only. A PR opened from a fork is not seen, and its dev job closes as if no PR were open.
  - When the record update inside `resume` succeeds and the job file write after it fails, the record says running and nothing was sent; `resume` then prints `busy:` until that agent is stopped with TaskStop or the cockpit exits.
  - A launch record that cannot be read makes the job busy, not refused: `resume` prints `busy:` every time and `close` refuses too, the job's cards read "(job running)" and are neither asked nor refused, and `pending.mjs list` names no reason for it (seen on a garbled record, 2026-11-12). The way out is to repair or remove that record; a removed record turns into a `refused:` with no launch record.
  - A card that asks to start another role's job can start that job twice when the cockpit is interrupted between `job.mjs start` and the card's `card-note`.
  - Two resumes from a caller with no identified cockpit, of a job with no live agent, both pass, because the first leaves no cockpit pid that marks the job as starting. A real cockpit always has a claude pid.
- The design was settled after six review rounds, each of which opened new surface; the live check after release is the next evidence, not another review round.
- Weakest link: no live cockpit has run this yet. The live check after release must show a question card asked on the job's notification turn, the answer reaching the job through SendMessage, and the gate log's `ask-cards` lines.
