# 0019: Jobs run as native background subagents

Status: accepted (2026-11-11, user decision; probed 2026-11-11, built 2026-11-11); supersedes the launch adapters of [ADR 0018](0018-jobs-are-visible-sessions-opened-by-optional-runtime-adapters.md) (T3 thread, herdr pane, printed command)

## Context
- ADR 0018 opened each job as a session of its own: a T3 thread on a `tedy-<role>` provider instance, a herdr pane, or a `claude --agent tedy:<role> --settings <file>` command the user ran. That needed four T3 instances written into T3's settings file, a settings file per role, a launch spec, per-job claude pids and the kit signalling them, and herdr calls.
- The user decided on 2026-11-11: "Tôi thích phương án sub-agent hơn vì nó native hơn", and chose "Subagent cho mọi job" over keeping the thread and pane adapters, knowing that the user cannot type into a native subagent inside T3, that a background subagent cannot ask, and that a job ends with the cockpit session.
- A probe in a T3 cockpit on 2026-11-11 (Probe evidence below) showed a body-less `tedy:pm` background subagent keeps the Claude Code system prompt, sees the kit skills it may invoke, keeps the Agent tool, has no AskUserQuestion, has its role-gate ask surfaced in the cockpit thread, and resumes with its history through SendMessage.

## Decision
- **Every job is a background subagent of the cockpit.** `job.mjs start` writes the job file and its launch record as before, makes a dev job's core worktree, and prints one Agent call spec: `{ subagent_type: "tedy:<role>", run_in_background: true, name: "<role>-<yymmddhhmm>-<slug>", description: "<role> <up to four title words>", prompt }`. The name comes from the job file's name, cut to 32 characters with the stamp kept, so jobs of the same title started in different minutes differ; `start` refuses, and removes the job file it just made, when an open job already has that name (titles sharing their first words in one minute). The cockpit calls the Agent tool with it.
- **The prompt starts with the launch form `Job file "<file>"`**, names the plugin root and `jobs.md` section "Job", and then the role's skill: pm and review invoke `tedy:pm` and `tedy:review-pr` with the Skill tool; dev reads the absolute path of `skills/dev/SKILL.md`, because that skill sets `disable-model-invocation` and the probe's Skill tool did not list it; devops has no skill.
- **Binding by agent id.** A hook event whose `agent_type` is `tedy:<role>` and that carries `agent_id` binds that id to the job named by the launch form at the head of the agent's own transcript: `agent_transcript_path` on SubagentStop, else `<project>/<session_id>/subagents/agent-<agent_id>.jsonl` beside the main transcript. The record gets `agent_id`, the parent `session_id`, the agent transcript and the cockpit's claude pid and start time. No SubagentStart hook: the canon keeps per-spawn events out of `hooks.json`, and the first PostToolUse binds instead.
- **Status.** `running` after a tool of the agent, `waiting: permission` on a Notification of that agent, `idle` on SubagentStop (matcher `^tedy:(pm|dev|review|devops)$`), `stopped` when a TaskStop in the cockpit session that runs the agent carries its exact agent id as a string value of `tool_input`. The tools reference says TaskStop accepts "a named background agent by agent ID or name" but names no input field, so the hook cannot tell a name field from any other string and matches the agent id only; a TaskStop by name stops the agent but leaves the record's state as it was. `stopped` is sticky: a later tool, permission or stop event of the same agent leaves it `stopped`, so a late PostToolUse cannot make `close` refuse a stopped job; only `job.mjs resume` moves it (SendMessage path to `running`, fresh Agent path to a new agent). The docs say a SendMessage to a TaskStop'd agent resumes it once its stopped run has exited, so a SendMessage the cockpit sends without `job.mjs resume` leaves the record `stopped` while that agent runs again; jobs.md has the cockpit send answers only through `resume`. A bound agent's later events move its state by `agent_id` alone. `list` shows `lost (cockpit gone)` once the recorded cockpit claude has ended and the job is not done.
- **Questions go through question cards, answers and rework through SendMessage.** A job writes a `question` card and ends its turn. `job.mjs resume` appends the note and prints a SendMessage call to the agent id when the caller is the cockpit that runs the agent, refuses when another live cockpit runs it, and otherwise prints a fresh Agent spec carrying the note.
- **Close.** `start`, and a `resume` that prints a fresh Agent spec, record the claude process that ran them as the job's cockpit, so a job whose agent has not bound yet still names its cockpit. `close` refuses and writes nothing in three cases: the job's agent is running or waiting in a live cockpit (the cockpit stops it with TaskStop first); the job is `not started` while the cockpit that started it is alive, because its agent may be starting; the job's agent is bound but the launch record holds no cockpit pid, because the kit cannot tell whether that agent runs. In the last two the user ends the agent or the cockpit session first. A job file with no launch record still closes. A record that no agent bound and that holds no cockpit pid, because `start` ran outside claude, closes with the line "nothing was bound to this job, so nothing was signalled". Otherwise `close` marks the file closed and prunes the core worktree with the same safety checks as before. `prune` keeps the worktree in each case `close` refuses: an agent running or waiting in a live cockpit, a job `not started` while its cockpit runs, and a bound agent with no cockpit pid. A `resume` that prints SendMessage sets the record's state to `running`, so `close` refuses until the agent is idle or stopped again.
- **`/tedy:pending` closes with plain `close`.** It used `close --if-ended`, which refused when no claude pid was recorded and never removed the worktree. Plain `close` now refuses the same cases (a bound agent with no cockpit pid recorded, an agent that runs or may be starting) and removes a core worktree only through the prune checks, so `--if-ended` is no longer needed and is gone.
- **Role gate.** A subagent takes the role of its `agent_type: tedy:<role>` only when all three hold: a kit launch record of that role binds it (the record holds its `agent_id`, or its own transcript starts with the launch form naming a job file whose record has that role and no other agent), the project map has `jobs: true`, and its parent session is not a session the map lists in `sessions`. In every other case the gate judges it as before the jobs change: by its parent's role file, else by its session's name, else as the cockpit. The gate resolves the map for this check with the role gate off too, so the close ask holds in every mode. It writes no role file for the cockpit's session.
- **Every job keeps the Agent tool.** The aim was to let every job spawn only `tedy:reviewer`, with `tools: Agent(tedy:reviewer)`. The sub-agents docs rule that out for a subagent definition: "The `Agent(agent_type)` allowlist syntax applies only to an agent running as the main thread with `claude --agent`. In a subagent definition, listing `Agent` in `tools` lets that subagent spawn subagents of its own while the depth limit allows it, but any type list inside the parentheses is ignored." Setting `disallowedTools: Agent` on the pm, review and devops agents was tried and taken back on 2026-11-11: it kept a review job from spawning the `tedy:reviewer` lenses of `/tedy:review-pr` step 6 and a pm job from spawning the spec lens of `reconcile-flow.md` step 7. No job agent sets `tools` or `disallowedTools`. A `tedy:reviewer` child of a job stays under the read-only reviewer gate, which keys on `agent_type` alone; a child whose type is not `tedy:` is judged as the cockpit (Threat model).
- **Kit-state asks replace the role settings files' ask rules.** Those files gave every job `ask: ["Bash(git *--output*)", "Edit(/<profile>/**)", "Edit(/<state>/**)"]`. The role gate now asks a bound job agent, in every mode and with the role gate off, before a Bash segment that runs git with any `--output…` option, and before an Edit, Write or NotebookEdit of a path under the profile dir or the state dir. The cockpit is not asked.
- **Removed:** the t3, herdr and print adapters (`job-adapters.mjs`), `job.mjs t3-instance` and `--write`, `job.mjs settings` and the role settings files, the launch spec command line, per-job pid signalling and the close refusal by process ancestry (a job no longer is a process of its own), `--via`, `--t3`, `--json`, `--permission-mode`, `--if-ended`, the herdr notification, the T3 instance labels and setup step, and the status hooks on SessionStart, Stop and around AskUserQuestion.
- **Jobs from older kits.** v0.2.24 and v0.2.25 wrote `permission_mode` and, in v0.2.24, `session_id` into a job file's header. The header read still takes both, so no key an older kit wrote stops it before `repo`, `branch` and the rest, and `resume` sees no false difference from the launch record. `start` writes neither. `via` and `herdr` were launch record keys, never header keys. A launch record those kits wrote has no `agent_id`, no `cockpit_pid` and no `agent_name`, which this kit's `start` always writes; such a job has no subagent of this design. `close` closes it without signalling anything, removes its core worktree only through the prune checks, leaves a worktree T3 or a herdr pane made, keeps the core worktree while the record's `pid` and `pid_start` still name a claude process (as v0.2.25's `prune` did; `prune` keeps it too), and prints "this job came from an older kit; nothing was signalled, and any session it had (a T3 thread, a terminal pane or a claude session) is the user's to end". `resume` prints a fresh Agent spec carrying the note and writes the agent name into the record, so the job is this kit's from then on.

## Prior art

- Claude Code subagents docs (Anthropic docs, studied 2026-11-11, via web)
  - https://code.claude.com/docs/en/sub-agents "Background subagents surface every permission prompt in your main session."
  - https://code.claude.com/docs/en/sub-agents "Apart from `Agent` and `ExitPlanMode`, which follow the first filter's conditions wherever the subagent runs, a background subagent keeps every MCP tool but only these built-in tools: `Read`, `Grep`, `Glob`, `LSP`, `Bash`, `PowerShell`, `Edit`, `Write`, `NotebookEdit`, `WebFetch`, `WebSearch`, `TodoWrite`, `Skill`, `ToolSearch`, `EnterWorktree`, `ExitWorktree`, `Monitor`, `TaskStop`, `SendMessage`, and `Artifact`"
  - https://code.claude.com/docs/en/sub-agents "When Claude sends a completed subagent a message with the `SendMessage` tool, the subagent resumes in the background without a new `Agent` invocation."
  - https://code.claude.com/docs/en/sub-agents "Each transcript is stored as `agent-{agentId}.jsonl`."
  - Lesson: a background subagent's prompts land in the cockpit, it cannot ask, and SendMessage is native rework with the agent's history. The built-in list above excludes `Agent`, which the docs filter separately; the observed tool set of a job agent is the probe's (Probe evidence), and it includes `Agent`, so a job can spawn subagents unless its definition removes the tool. ADR 0018 read the first fact as a reason against subagents; the user weighed it the other way.
  - https://code.claude.com/docs/en/sub-agents "In a subagent definition, listing `Agent` in `tools` lets that subagent spawn subagents of its own while the depth limit allows it, but any type list inside the parentheses is ignored."
  - Taken: jobs as background subagents, questions on cards, rework through SendMessage, binding from the agent's own transcript, and the plain Agent tool for every job, since the platform ignores an `Agent(tedy:reviewer)` allowlist in a subagent.
- Claude Code tools reference (Anthropic docs, studied 2026-11-11, via web)
  - https://code.claude.com/docs/en/tools-reference "`TaskStop` | Stops a running background task by ID. It also accepts an agent-team teammate or a named background agent by agent ID or name."
  - Lesson: TaskStop takes an agent's id or name, but the reference names no input field.
  - Taken: the status hook marks a job `stopped` only on its exact agent id, and the cockpit passes that id.
- Claude Code hooks reference (Anthropic docs, studied 2026-11-11, via web)
  - https://code.claude.com/docs/en/hooks "The `transcript_path` is the main session's transcript, while `agent_transcript_path` is the subagent's own transcript stored in a nested `subagents/` folder."
  - https://code.claude.com/docs/en/hooks "SubagentStart hooks receive `agent_id` with the unique identifier for the subagent and `agent_type` with the agent name that the matcher filters on."
  - Lesson: SubagentStart carries no prompt, so the prompt comes from the agent's transcript; tool events inside a subagent carry `agent_id` and `agent_type`.
  - Taken: bind on the agent's first PostToolUse or its SubagentStop, matcher anchored as `^tedy:(pm|dev|review|devops)$` for the plugin-scoped name.

## Consequences
- **Supersedes ADR 0018's launch adapters.** These no longer apply: the T3 thread and its `tedy-<role>` instances, `t3-instance --write` and the kit's write to T3's settings file, the herdr pane, agent and notification, the printed command, the role settings files and their allowlists, `--via`, `--t3`, `--json`, `--permission-mode`, `--if-ended`, signalling a job's claude process, and the close refusal by process ancestry. ADR 0018's "jobs ask in their own window" is reversed again: a job cannot ask.
- **Kept from ADR 0015 and 0018:** job files and their sections, the launch record keyed by the job file, the inbox cards, the role gate and its close ask, record locks, core worktrees and their prune safety, `done` and `stop`.
- **Jobs end when the cockpit session ends.** A long dev job dies with the cockpit; `resume` then starts a fresh agent from the job file and its note.
- **Permissions follow the cockpit.** Claude Code ignores `permissionMode` for plugin subagents, so a job runs in the cockpit's mode. In `default` mode each prompt waits in the cockpit, and a grant for the session covers the cockpit and every job. The cockpit never answers a job's permission card for the user.
- **Cost:** a job's tool output stays out of the cockpit's context; each completion notification enters it.
- **Threat model.** The kit defends against a job acting on another job by mistake: the role gate asks before a literal `job.mjs close` from a job in every mode, and `close` refuses any job whose agent still runs. Not stopped: a job that marks another job `done` or `stopped`, rewrites a launch record through a shell command, or points `TEDY_STATE_DIR` elsewhere. Accepted ceiling: a subagent a job spawns itself whose type is not `tedy:` has the cockpit's session, so the role gate judges it as the cockpit, and the `job.mjs close` and kit-state asks do not reach it; a job that routes work through a general subagent, deliberately or by mistake, gets the cockpit's verdicts. A `tedy:reviewer` child stays under the reviewer gate, which refuses its Bash commands other than reads. A job that deliberately attacks another job under `bypassPermissions` is beyond what a same-user hook can prevent.
- **Not yet exercised live:**
  - which transcript `transcript_path` names on a tool event inside a subagent: the docs define it as the main transcript only for SubagentStop, so binding takes it as the agent's own when its name is `agent-<agent_id>.jsonl` and derives the agent's path from it otherwise; if both miss, the job binds only at its first SubagentStop and reads `not started` until then, and `close` refuses it while the cockpit that started it is alive;
  - whether a Notification for a background subagent's permission prompt carries its `agent_id` (if not, `waiting: permission` never shows and the job reads `running`);
  - whether SubagentStop fires after TaskStop, and the TaskStop input field that names the agent (the docs name none; the hook matches any string value of `tool_input` against the agent id only);
  - that the hook's `agent_id` is the id SendMessage takes (derived from the docs naming transcripts `agent-{agentId}.jsonl` and from the transcripts read on this machine, below);
  - a real dev job working in its core worktree through `git -C`;
  - an agent that dies without SubagentStop leaves its job `running`, so `close` refuses it until the cockpit session ends.

## Probe evidence
OBSERVED, from a probe in a T3 cockpit on 2026-11-11, reported by the user:
- A body-less `tedy:pm` background subagent keeps the Claude Code system prompt, so the agent files need no body.
- Its Skill tool lists `tedy:pm` and `tedy:review-pr`, but not `tedy:dev` (the dev skill is not model-invocable).
- Its tools are Agent, Bash, Edit, Read, Skill, ToolSearch, Write, MCP tools, and deferred EnterWorktree, ExitWorktree, Monitor, SendMessage, TaskStop, WebFetch and WebSearch. AskUserQuestion is missing. This observed set is the fact the design rests on; the docs' background list quoted under Prior art leaves `Agent` out because it filters `Agent` separately. No job agent's definition removes it.
- A role-gate `ask` on its Write was logged with agent `tedy:pm` and surfaced in the cockpit thread as a T3 approval card.
- SendMessage resumed it with its history.
- No session-roles file was written for it.

OBSERVED on 2026-11-11 while building: the subagent transcripts of a live session on this machine sit at `<project>/<session id>/subagents/agent-<id>.jsonl`, each first line a `user` entry with `isSidechain: true`, the agent id without an `agent-` prefix, and the spawning prompt as its string content.
